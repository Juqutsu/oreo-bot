# CLAUDE.md — Oreo Bot

> **MAINTENANCE RULE (always applies):** After completing any prompt/task in this repo, update this file with new information learned — new commands, changed invariants, fixed/new bugs, schema changes, config keys, deploy changes. Keep it factual and current; remove entries that become obsolete. This file is the single source of truth for working on Oreo.

## What Oreo is

German-language Discord **security & moderation bot** ("Wachhund des Home Servers") — one of several single-purpose bots on the Home Server (others handle fun/music/etc., see `bot.md` for the design spec). Discord.js **v14**, **CommonJS**, Node >= 20 (Docker uses node:22-alpine), **MySQL** via `mysql2/promise`. All user-facing text is **German**.

Scope: moderation commands (ban/kick/warn/timeout/mute...), warn escalation, report system, Discord-native AutoMod integration, toxicity word filter, anti-raid + captcha verification, invite tracking, welcome/leave cards (canvas), server/message logging, voice speech-recognition commands (de-DE).

## Commands

```bash
npm start        # node --env-file=.env index.js
npm test         # tests/run.js → runs every tests/smoke/*.js as child process (needs MySQL)
docker compose up -d --build   # prod-style run (external network discord_bot_net, MYSQL_HOST=mysql)
```

Deploy: push to `main` → GitHub Actions (`.github/workflows/deploy.yml`) runs smoke tests against MySQL 8.4 service, then SSH-deploys (`git pull` + docker compose) to the server at `/app/oreo-bot`.

## Environment (.env — see .env.example)

Required: `DISCORD_TOKEN`, `CLIENT_ID`, `GUILD_ID`, `MYSQL_HOST/USER/PASSWORD/DATABASE` (missing → exit 1 at startup).
Optional: `MYSQL_PORT` (3306), `MODLOG_CHANNEL_ID` (global fallback mod-log — **applies to every guild that hasn't set its own** via `/config channel set type:modlog`, cross-guild leak risk), `DEVELOPER_ID` (**owner-tier backdoor in every guild**, also bypasses /setup gate — security relevant).

## Startup flow (index.js)

env check → create Client (privileged intents: GuildMembers, MessageContent, GuildVoiceStates + automod/invites/moderation; partials: `Message`, `GuildMember`, `User`) → `addSpeechEvent` (de-DE speech recognition, loaded unconditionally) → load commands/events (`loadEvents.js` wraps every handler's `execute()` in `.catch()`, logging `[events] Handler <file> (<name>) failed:` instead of letting a rejection escape) → DB ping → `ensureSchema()` (replays `server/schema.sql` every boot, swallows errnos 1060/1061/1091/1146) → deploy slash commands **to the single GUILD_ID only** → login. Events, however, fire in *all* guilds — the bot is single-guild by config, multi-guild by behavior.

Process-level safety net: `process.on('unhandledRejection', ...)` logs and continues (does not exit); `process.on('uncaughtException', ...)` logs and calls `process.exit(1)`.

## Critical invariants — read before touching interaction code

1. **Auto-defer:** `index.js` defers **every** slash command **ephemerally** before `execute()`, unless the command opts out by exporting `showsModal` — either `true` or a `(interaction) => boolean` function (for per-subcommand cases). When `showsModal` (or its return value) is truthy, the auto-defer is skipped so the command can call `showModal()`. If the `showsModal` function throws, `index.js` catches it, logs the error, and falls back to deferring normally (safe default). New modal commands declare `showsModal` on their own module and never need to touch `index.js`.
2. **Monkey-patched reply:** `interaction.reply` is patched to become `editReply` once deferred/replied. Consequence: commands can never produce a *public* reply through `reply()` (defer is ephemeral); `flags` passed later are dropped.
3. **Component routing:** buttons/selects/modals chain through `dispatch()` of `src/interactions/{report,announcement,captcha,welcome,voiceconfirm}.js` (customId prefixes `report:`, `announcement:`, `captcha_`, `welcome:`/`leave:`, `voiceconfirm:`); unhandled → "Unbekannte Interaktion". New component features: add a dispatcher to the chain in index.js.
   - `/announcement`'s `showsModal` (`src/commands/announcement.js`) is a **function**, not a boolean: `(interaction) => ['create', 'edit'].includes(interaction.options.getSubcommand(false))` — only those two subcommands skip auto-defer to call `showModal()`; `delete`/`list` go through the normal ephemeral auto-defer.
4. **Autocomplete enforces command tier:** `index.js` checks `command.requiredTier` via `perms.hasTier(...)` before calling `command.autocomplete()`; a disallowed caller gets an empty `interaction.respond([])`, not real data (e.g. ban list in /unban, wordlist in /automod). Commands without a `requiredTier` (e.g. `/warnings`) have nothing to gate.
5. **Duration syntax** (`src/duration.js`): `s / m / h / t / d / w` — German `t` = Tag, and `d` is accepted as a plain alias of `t` (both map to 86 400 000 ms). Max **timeout**: 28d (`MAX_TIMEOUT_MS`, Discord API hard limit). Max **temp-ban/temp-mute**: 365d (`MAX_TEMP_MS`) — ban.js/mute.js enforce this cap.
6. **Permission tiers** (`src/perms.js`): `supporter < moderator < owner` from `role_permissions` table — tier assignments per bot.md: warn/timeout/untimeout = supporter; ban/unban/kick/softban and other mod tools = moderator; config/automod/setup = owner. Guild owner and `DEVELOPER_ID` are always `owner`. `TIER_PERMISSIONS` (also in `perms.js`) maps each tier to a Discord `default_member_permissions` value used by `loadCommands.js` for client-side command visibility only — real authorization is always `requireTier`/`hasTier` (DB-backed). Three commands export no `requiredTier` at all: `/warnings` (self-service — defaults to the caller's own warnings, only gates *other* users' warnings via an in-command `perms.hasTier` check, see item 12), `/report` (open to every guild member by design — anyone can file a report), and `/setup` (gated instead via `defaultMemberPermissions: Administrator` for client-side visibility plus an inline guild-owner/`DEVELOPER_ID` check in `execute`, since it bootstraps `role_permissions` before any tier exists). A "Ramen level" link can grant supporter via shared `guild_users.level` (see Database section — the column is now defined in `server/schema.sql`, so it also works on a standalone DB).
7. **Cases** (`src/cases.js`): all punishments write to `infractions` with a per-guild atomic `case_number` (LAST_INSERT_ID trick, transactional). Temp punishments pass `expiresInMs` (ms from now); `createCase` computes `expires_at` **DB-side** via `DATE_ADD(NOW(), INTERVAL ? SECOND)` so no JS `Date` ever crosses the wire (avoids Node-local-vs-MySQL-server timezone skew). **New code must use `expiresInMs`, never pass a JS `Date`** — the legacy `expiresAt: Date` param still exists only for callers not yet migrated. `reason` is defensively truncated to 512 chars inside `createCase` regardless of caller (column is `VARCHAR(512)`); slash-command reason options also carry `.setMaxLength(512)`. If `createCase` fails **after** the Discord-side action already succeeded, ban.js/mute.js/timeout.js revert it (unban/role-remove/timeout-clear) rather than leaving an untracked, silently-permanent punishment. ban.js/mute.js also call `cases.deactivateActiveInfractions(guildId, targetId, type)` before creating a fresh temp punishment, so a stale active row can't later cause `background.js` to auto-expire the wrong case.
8. **Background loop** (`src/background.js`): one 60s `setInterval`, guarded by a process-local `running` flag so overlapping ticks are skipped (still **not** safe across two bot instances on one DB — no distributed lock). Each tick: expires temp-bans/mutes (system unban/unmute case + modlog), deactivates expired `type='timeout'` rows via a bulk `UPDATE` (no Discord call — Discord lifts timeouts itself, no system case needed), applies warn decay, then sweeps expired captcha verification deadlines (kick + per-user temp-channel cleanup — see invariant 15).
9. **Config caching** (`src/config.js`): the per-guild config row and the normalized bad-words list are cached in-process for 30s (`ROW_CACHE_TTL_MS`). Every setter in `config.js` calls `invalidateGuildRowCache`/the bad-words equivalent right after its `UPDATE`. **Any code that runs a raw `UPDATE guilds SET ...` outside `config.js`'s own setters (e.g. the direct-column updates in `src/commands/config.js`) must call the exported `invalidateGuildRowCache(guildId)` itself**, or reads can serve stale data for up to 30s — already done for all such sites in `src/commands/config.js`, but keep it in mind for new ones. Toxicity/bad-word matching should go through `getNormalizedBadWords(guildId)` (pre-normalized, cached) rather than re-normalizing every bad word per message. Both `readGuildRow` and the `getBadWords` cache-fill dedupe concurrent cold-cache calls for the same `guildId` via a module-level `inflight` `Map` (`rowInflight`/`badWordsInflight`): a second caller arriving while a fetch is already in flight awaits the same promise instead of issuing its own duplicate `SELECT`; the map entry is removed in a `finally` once the fetch settles. **Invalidation is now safe against in-flight races:** `invalidateGuildRowCache`/`invalidateBadWordsCache` delete the cache entry, **clear the in-flight promise map entry**, and increment a per-guild generation token. Before the SELECT, the fetch captures the current generation; after the SELECT, it only writes to cache if the generation is unchanged. This ensures that a fetch racing an invalidation cannot overwrite the cache with stale data — the delayed write is silently skipped.
10. **Shared moderation helpers — new code must use these, not hand-roll the pattern:** `sendModLog(interaction, embedParams)` (`src/modlog.js`) for the fetch-channel → build-embed → send → ephemeral-warning-on-failure tail; `validateModTarget(interaction, target, { action, requireMember })` (`src/modGuards.js`) for the self/bot/owner/hierarchy/bot-ability guard sequence (per-action German texts preserved in an `ACTION_RULES` registry; `/untimeout` is deliberately **not** converged — its custom "not currently timed out" check doesn't fit the shared guard order); `resolveAuditExecutor(guild, auditLogEventType, targetId, opts)` (`src/auditExecutor.js`) for the `*-log` event handlers' "who did this" audit-log lookup. `cleanup`/`lockdown`/`slowmode`/`unlock` still post their modlog entries inline (not via `sendModLog`), with a silent-skip-on-unset shape rather than the ephemeral-warning shape the rest of the mod commands now have.
11. **In-memory state lost on restart:** captcha's own `pendingPuzzles` (invariant 14), report cooldowns, invite cache, anti-raid state, channel-hopping history — none of these re-hydrate from DB. (Captcha verification deadlines used to be in this list too — a 15-min `setTimeout` per join — but are now DB-persisted, see invariant 15.) Channel-hopping history is keyed `` `${guildId}:${userId}` `` (not bare `userId` — avoids cross-guild false triggers), stores only `{ timestamp, channelId, messageId }` per entry (not the full Discord `Message` object), and is swept every 60s to drop empty/stale keys, bounding memory growth.
12. **Moderation UX mechanics:** ban.js/kick.js send a best-effort DM to the target (`.catch(() => null)`) **before** executing the punishment, since a banned/kicked user can no longer be DMed after (mute.js does not — the user stays in the server and remains DMable). `/warnings` needs no tier: it defaults to the caller's own warnings and only runs an in-command `perms.hasTier(..., 'supporter')` check when looking up *someone else's*. `src/interactions/report.js`'s modal-resolve flow runs the same `escalations.applyEscalation` warn.js uses when the chosen action is `warn`. If a report's channel post fails after its DB row was already inserted, `src/commands/report.js` deletes that row (`reports.deleteReport`) and tells the reporter explicitly their report was **not** saved, rather than leaving a silent orphan. A member who rejoins while an active `mute` infraction exists has the Muted role re-applied automatically (`guildMemberAdd.js`); the mod-log entry only claims success if `roles.add` actually succeeded, otherwise it posts an explicit "could not re-apply" warning instead of a phantom success line.
13. **`/announcement` lifecycle** (`src/commands/announcement.js`, `src/interactions/announcement.js`, `src/announcements.js`): subcommands `create`/`edit`/`delete`/`list`, all `requiredTier: 'moderator'` — every moderator (not just the original author) may edit or delete any announcement; attribution is via the modlog embed (`edited_by` column), not an author-only gate. `create` and `edit` open a modal (title/description/image-url) whose submit renders an **ephemeral preview** (embed + Posten/Bearbeiten/Abbrechen/✏️ buttons) rather than posting immediately.
    - **Preview sessions** live in an in-process `Map` (`previewSessions`, keyed by nonce = the first modal submit's `interaction.id`) with a 10-minute TTL (`PREVIEW_TTL_MS`), swept every 60s; **lost on restart** — a mod mid-edit when the bot redeploys just has to redo `/announcement edit` (deliberate design decision, not a bug — see "Explizit NICHT in diesem Plan" for what was ruled out instead: restart-safe drafts).
    - The "✅ Posten"/"✅ Übernehmen" button synchronously sets `session.posting = true` **before** any `await`, closing the double-click race where two near-simultaneous clicks both pass the session/user checks — the loser gets "⏳ Wird bereits gepostet …" instead of double-posting/double-writing. `handlePreviewButton` wraps the `handlePostCreate`/`handlePostEdit` dispatch in `try { … } finally { if (previewSessions.has(nonce)) session.posting = false; }` — this is now the **only** place that resets the flag (the handlers' own per-failure-branch resets were removed as redundant): the success path deletes the session first, making the finally-reset a no-op, and every failure path (retryable or terminal) is covered by the finally instead of a hand-rolled reset at each `return`.
    - CustomId families: `announcement:modal:<create|edit|resume>:*` (modal submits — `resume` is the re-edit-from-preview path, reusing the original nonce), `announcement:preview:<post|reedit|cancel>:<nonce>` (preview buttons), `announcement:delconfirm:<yes|no>:<id>` (delete confirmation, also reused as the orphan-cleanup button when an edit's target message is manually gone).
    - Editing preserves the **original `created_at`** (embed timestamp unchanged) and stamps the footer with `🐾 Oreo • bearbeitet` (vs plain `🐾 Oreo`); the edit only touches `embeds` on `message.edit()` — the message's `content` (ping line) is left untouched, so a re-edit never re-pings.
    - The delete-confirmation buttons (`delconfirm:yes/no`, `yes` branch only) now have their own synchronous claim, mirroring `session.posting` but keyed by `announcementId` since there's no session object: a module-level `pendingDeletes = new Set()` in `src/interactions/announcement.js` is checked/added before any `await` and cleared in a `finally` around the whole handler body — a double-click's loser gets "⏳ Wird bereits gelöscht …" instead of racing through the delete.
    - `truncateForDiff` (300-char cutoff + `'…'`, used for the edit mod-log Alt/Neu diff fields) is exposed via `_internal.truncateForDiff` for `tests/smoke/announcement_flow.js` to assert directly (301-char input → 300 chars + `'…'`, length 301).
14. **Captcha answers are server-side** (`src/interactions/captcha.js`): `generatePuzzle(guildId, userId, attempt)` stores `{ correctEmoji, options, attempt, expiresAt }` in a module-level `pendingPuzzles` `Map` keyed `` `${guildId}:${userId}` `` (same Map+TTL+unref'd-sweeper shape as `previewSessions`, invariant 13) with a 15-minute TTL (`PUZZLE_TTL_MS`), swept every 5 minutes. Buttons only carry `captcha_pick_<userId>_<index>` — no answer or attempt count in the customId, closing the selfbot auto-solve hole (a script reading the component payload could previously read `captcha_correct_*`/`captcha_wrong_*` off the other buttons without ever seeing the puzzle image). All three call sites (`captcha_global_start`, `captcha_start_<userId>`, and re-rolling on a wrong pick) look up any existing non-expired entry first so the attempt counter carries over across regenerations — a user can't reset their `Versuch x/3` count by re-triggering the puzzle. On dispatch, an expired/missing entry replies "Captcha ist abgelaufen" instead of silently 500ing; a correct pick deletes the entry before running the existing role-assignment flow, a wrong pick either re-rolls (attempt < 3) or deletes the entry and kicks (attempt >= 3). Module exports `_internal: { generatePuzzle, pendingPuzzles }` for `tests/smoke/captcha_answers.js`.
15. **Persistent verification deadlines** (`src/verifications.js`, table `pending_verifications`): `guildMemberAdd` calls `trackJoin(guildId, userId, channelId, minutes)` instead of the old 15-minute `setTimeout` kick — the deadline (`DATE_ADD(NOW(), INTERVAL ? MINUTE)`) is computed **DB-side** and survives restarts. Since Task 12 (see invariant 16), `guildMemberAdd.js` always passes `channelId = null` — the verify channel is now the one shared per-guild channel, which must never be deleted by the sweep. (`background.js`'s channel-delete-on-expiry branch, guarded by `if (row.channel_id && ...)`, is now effectively dead code for new joins — kept because rows written before the Task 12 deploy may still carry a real per-user `channel_id` until they expire out.) `captcha.js`'s `pick` handler calls `markVerified(guildId, userId)` (a `DELETE`) as the **first** action on a correct solve — before any role assignment — so a user who solved the captcha can never be deadline-kicked even if role assignment subsequently fails; the 3-fails kick branch calls `remove` (alias of `markVerified`) right after `member.kick(...)`. `background.js`'s `runDecayAndExpiry` section 5 sweeps `listExpired()` every tick: kicks the member (if still present), posts a modlog line, and **always** calls `remove()` afterwards regardless of whether the guild/member was still found, so a stale row can't retry forever. `pending_verifications` has `FOREIGN KEY (guild_id) REFERENCES guilds(guild_id) ON DELETE CASCADE` like the other per-guild tables.
16. **Shared verify channel with creation-dedup** (`src/composables/verifyChannel.js`): `getOrCreateSharedVerifyChannel(guild)` replaces the old per-joiner `verify-<userId>` channel creation in `guildMemberAdd.js` — a raid wave of N joins used to mean N `channels.create` calls (self-inflicted rate-limit DoS, see former Known-issues entry). It first checks `config.getCaptchaChannelId(guildId)`/fetches that channel; if missing, concurrent callers for the same guild share **one** in-flight creation `Promise` via a module-level `creating` `Map` (keyed by `guildId`, cleared in a `finally`) — only the first caller actually creates the channel (name `oreo-verify`, `@everyone` can view/read history but not send, bot gets full manage perms) and calls `config.setCaptchaChannelId`; every other concurrent caller awaits the same promise and gets the same channel back. The channel's button (`captcha_global_start`) and `captcha.js`'s existing global-start handling are unchanged. `guildMemberAdd.js` DMs the joiner a link to this channel and no longer builds any embed/button itself for the join path.
17. **Speech privacy gate** (`src/commands/voice.js`, `src/events/speech.js`, `src/commands/config.js`): `/voice join` checks `config.getVoiceRecEnabled(guildId)` first and refuses to call `joinVoiceChannel` (ephemeral German privacy explanation) when disabled, so no audio is ever streamed to the `discord-speech-recognition` (Google STT) backend (wired up in `index.js` via `addSpeechEvent(client, { lang: 'de-DE' })`) as long as the feature was already off before joining — that gate is airtight. Mid-session disabling is handled by `/config voice enabled:false` (`handleVoiceSet` in `src/commands/config.js`), which immediately calls `getVoiceConnection(guildId)?.destroy()` right after persisting the flag, so the connection is torn down by the disable action itself, not by the next utterance. `speech.js`'s disabled branch (`if (!enabled)`, which also calls `getVoiceConnection(guildId)?.destroy()`) is a belt-and-braces fallback for any path that flips the flag without going through that command — because the `discord-speech-recognition` library buffers a user's audio and sends it to Google STT *before* emitting the `speech` event, this fallback can still let at most the one already-in-flight utterance reach STT before the connection dies.
18. **Word-boundary voice commands + confirmed voice-mute case records** (`src/events/speech.js`, `src/interactions/voiceconfirm.js`): matching is no longer substring-based — `cleanText.split(/[^a-zäöüß0-9-]+/)` tokenizes the STT transcript, `oreoIdx = words.indexOf('oreo')` locates the trigger word, and only `words[oreoIdx + 1]` (the very next token) is checked against each command's word list (e.g. `['ban','bann','band','oreoban']`), with everything after that (`words.slice(oreoIdx + 2)`) used as the mute target name. This closes the false-positive hole where ordinary conversation containing "ban"/"mute"/etc. as a substring (e.g. "Oreo **Banane**") used to fire a command. Lockdown and voice-mute are destructive, so both now call `voiceConfirm.requestConfirmation({ textChannel, voiceChannel, requester, action, targetMember? })` instead of acting immediately — this posts a "Bestätigen"/"Abbrechen" button pair (`voiceconfirm:ok:<id>` / `voiceconfirm:no:<id>`) into the linked voice-rec text channel with a 60s TTL (`pending` Map + unref'd sweeper, same shape as `previewSessions`/`pendingPuzzles`); only the original requester or a Supporter+ may click, others get an ephemeral reject and the pending entry survives untouched. Unlock stays direct (restorative, not destructive). On confirmed voice-mute, `voiceconfirm.js` calls `targetMember.timeout(...)` + `voice.setMute(true, ...)`, then writes a real case via `cases.createCase({ type: 'timeout', durationMs: BigInt(...), expiresInMs: ... })` and posts a mod-log entry via `buildModLogEmbed({ action: 'timeout', ... })` (manual `config.getModLogChannelId` → `channels.fetch` → send, not `sendModLog` — the interaction is an unacknowledged `ButtonInteraction` at that point, and `sendModLog`'s failure path assumes an already-deferred/replied interaction). A `createCase`/modlog failure here is logged and swallowed (not reverted) rather than undoing the Discord-side timeout — unlike the slash-command mute path (invariant 7), since the confirmation UX has no natural place to report "the mute was undone" back to a voice channel.

## Database

MySQL, shared with the Ramen bot (`guild_users`, `user_cards`). Oreo tables: `guilds` (config + case counter), `infractions`, `reports`, `escalation_rules`, `role_permissions`, `automod_rules/_wordlist/_exemptions`, `bad_words`, `market_listings` (unused), `announcements` (posted embed announcements — soft-delete via `status ENUM('posted','deleted')`, `FOREIGN KEY (guild_id) REFERENCES guilds(guild_id) ON DELETE CASCADE`, `edited_at`/`edited_by` set on edit), `pending_verifications` (restart-safe captcha deadlines, PK `(guild_id, user_id)`, `idx_deadline` on `deadline_at`, same `ON DELETE CASCADE` FK — see invariant 15). All queries parameterized. `infractions.reason` is `VARCHAR(512)` — see invariant 7 for the defensive truncation and `.setMaxLength(512)` coverage. `guild_users.level` is queried by `src/perms.js` (Ramen-level → supporter grant) and is now defined in `server/schema.sql` (column on `guild_users` + a Stage 25 staged `ALTER` for existing DBs) — so the lookup works on both the shared Ramen DB and a fresh/standalone DB. On the shared DB the `ALTER` is a no-op (errno 1060 swallowed by `src/schema.js`).

## Testing

`npm test` needs a reachable MySQL (reads `.env` itself); `npm run test:local` starts the `docker-compose.dev.yml` dev MySQL container (`--wait`) and runs the same battery with `.env.test` — the easiest way to run the full suite locally end-to-end. Smoke tests mock discord.js objects and cover: duration parsing, escalations, modlog embeds, reports DAL, captcha+toxicity, channel hopping, account-age, join roles, message/server logging, stats, audit mirror, voice rec, announcements DAL (`tests/smoke/announcements.js`, needs MySQL), announcement preview/edit flow (`tests/smoke/announcement_flow.js`, no DB — embed builder, session TTL sweep, modal prefill, `truncateForDiff` truncation), captcha server-side puzzle answers (`tests/smoke/captcha_answers.js`, no DB — customId leak check, `pendingPuzzles` shape, attempt-count survives regeneration; see invariant 14), persistent verification deadlines DAL (`tests/smoke/verifications.js`, needs MySQL — `trackJoin` insert/upsert, `listExpired` past-deadline lookup, `markVerified` delete; see invariant 15), voice-command word-boundary matching + destructive-action confirmation routing (`tests/smoke/voice_rec.js`, no DB — asserts "oreo banane" no longer false-positives as a ban, and that lockdown/mute now post a `voiceconfirm` button prompt instead of muting directly; see invariant 18), voiceconfirm button dispatch (`tests/smoke/voiceconfirm.js`, needs MySQL — expiry, wrong-user rejection, cancel, confirmed mute writes a real case + modlog row via `cases.getCaseByNumber`, confirmed lockdown mutes non-staff/skips staff+bots, missing-target handling; see invariant 18). Mocks whose `member.guild.roles.cache` lacks a real Discord.js collection need a `find: () => undefined` stub (see `join_role.js`/`server_logging.js`) or the mute-rejoin path's `getMutedRole` fallback throws a caught-but-logged `TypeError`. Tests exercising the captcha `pick` path seed `captcha._internal.pendingPuzzles` directly (`captcha_and_toxicity.js`, `join_role.js`) rather than encoding an answer in a mock customId, since the answer no longer lives there. ## Conventions

- German for all user-facing strings, English for code/comments/logs (mixed today; keep German UX).
- Moderation commands: fetch target member with `.fetch().catch(() => null)` (not cache), check role hierarchy (target vs moderator AND vs bot), DM before punishing where the user can no longer be DMed after (ban/kick), then act, then `createCase`, then modlog embed. For ban/kick/softban/mute/warn/timeout/unmute this whole guard sequence is centralized in `validateModTarget` (invariant 10) — don't reimplement it inline in new commands.
- Commands export `{ data, requiredTier, execute }`; `requiredTier` is optional — its absence (e.g. `/warnings`) means the command is open to every guild member, and any tier gating for specific paths must be done manually inside `execute`. Events export `{ name, once?, execute }` with their own try/catch.
- Commit style: conventional-ish prefixes (`feat:`, `fix:`, `perf:`, `refactor:`, `docs:`), imperative mood.
